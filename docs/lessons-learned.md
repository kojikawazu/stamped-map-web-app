## 2026-10-17 数値入力を消すと未入力チェックをすり抜け、英語の検証メッセージが出ていた

### 概要

スポット登録・編集モーダルで緯度・経度を一度入力してから消して送信すると、「緯度を入力してください」ではなく zod の既定メッセージ `Invalid input: expected number, received string` が表示されていた。未入力チェックが `isNaN` で書かれており、`v-model.number` が書き戻す空文字 `""` を素通りしていた。

### 詳細

- 何が起きたか: 登録・編集の両モーダルで、数値入力を空にした場合だけ未入力の判定が効かず、英語のメッセージが利用者に出ていた。送信自体はスキーマ検証で止まるため、不正データの登録は起きていない。#28 の共通化前に書いた特性テストが赤になって発覚した。
- なぜ起きたか（根本原因）: Vue の `v-model.number` は、数値に変換できない入力（空欄など）を `NaN` ではなく**元の文字列 `""` のまま**書き戻す。未入力の判定 `form.latitude === undefined || isNaN(form.latitude)` は、`isNaN("")` が `""` を `0` へ型変換して `false` を返すため、どちらの条件にも当たらなかった。「空欄 = `NaN`」という思い込みでチェックを書き、空欄を実際に入れて確かめるテストが無かった。
- 教訓 / 次からどうする: 数値入力の未入力判定は、引数を型変換しない `Number.isFinite` で行う（数値以外・`NaN`・`Infinity` をまとめて弾ける）。フォームのテストでは「一度入力してから消す」操作を入れる（初期値の `undefined` だけを試すと、`""` が書き戻される経路を通らない）。共通化・リファクタの前には、現状の挙動を固定する特性テストを先に書く。
- 関連: `.claude/rules/frontend.md`「バリデーション」（`Number.isFinite`）、PR #98、issue #28

## 2026-10-17 HTML 全体への正規表現で書いた VTU テストが、色の壊れを検出できていなかった

### 概要

`SpotListItem` の「カテゴリ色をバッジに反映する」テストを、描画結果の HTML 全体に正規表現を当てて書いたところ、バッジの色を壊しても緑のままだった。わざと壊して確かめる（ミューテーション）までは気づけなかった。

### 詳細

- 何が起きたか: 初版のテストは `wrapper.html()` に `color: #3498DB` 相当の正規表現を当てていた。バッジの文字色を壊すミューテーションを入れてもテストが通った。PR 作成前のミューテーション確認で発覚し、修正してからマージした。
- なぜ起きたか（根本原因）: 正規表現の `color:` が、左ボーダーの `background-color:` の末尾部分にも一致した。同じ色を持つ別要素がある限り、検証したい要素が壊れても HTML のどこかで一致してしまう。テストが緑であることを「検証できている」ことの証拠として扱っていた。
- 教訓 / 次からどうする: VTU のアサーションは**検証したい要素を特定してから**行う（要素を取得し `element.style.color` 等を見る）。HTML 全体への正規表現・`toContain` で値を探さない。新しく書いたテストは、対象の処理をわざと壊して**赤になることを確かめてから**完了とする。
- 関連: `.claude/rules/testing.md`「コンポーネント（VTU）」、PR #97、issue #27

## 2026-10-17 git ls-files の既定出力が日本語パスをクォートし、Secret scan の検出が漏れる

### 概要

Secret scan（`scripts/check-tracked-secrets.sh`）を `git ls-files` の出力に正規表現を当てて書いたところ、日本語などの非 ASCII 文字を含むパスでは行末アンカー `$` が効かず、秘匿ファイルを検出できないことが分かった。

### 詳細

- 何が起きたか: 導入時の検証で、非 ASCII 文字を含むパス配下の `.env` が検出されないことが分かった（`日本語/.env` は `"\346\227\245...\.env"` と出力される）。そのまま入れていれば、該当するパスの秘匿ファイルが CI を素通りしていた。
- なぜ起きたか（根本原因）: `git ls-files` は既定（`core.quotePath=true`）で、非 ASCII 文字を含むパスを `"..."` で囲み、文字を 8 進エスケープして出力する。行末が `"` になるため、`\.env$` のような行末アンカー付きのパターンが一致しない。出力を「パスそのもの」として扱えるという前提が誤っていた。
- 教訓 / 次からどうする: `git ls-files` / `git diff --name-only` 等の出力をパターン照合に使うときは、`-z`（NUL 区切り。クォートしない）で取得する。検出系のスクリプトには、検出されるべきパス・されてはならないパスを並べた自己テストを置き、本検査の前に CI で実行する（`scripts/test-check-tracked-secrets.sh`）。
- 関連: `.claude/rules/security.md`「シークレット管理」、`.claude/rules/static-analysis.md`「秘匿ファイルの混入検出」、PR #91、issue #85

## 2026-04-04 CI の E2E でテスト用サーバーの起動に 6 つの問題が連鎖した

### 概要

GitHub Actions に Playwright E2E を追加した際、テスト用サーバーが起動しない・起動しても接続できない・接続できても画面が出ない、という問題が 6 つ連鎖し、解決に長時間を要した。いずれもローカルでは再現しなかった。

### 詳細

- 何が起きたか: 次の 6 つが順に表面化した（前の問題を解くと次が見える構造だった）。
  1. `pnpm dev` の `webServer` がタイムアウトした（CI はキャッシュが無く、初回の Vite コンパイルに 3 分以上かかる）
  2. ビルド済みサーバーがログを出さずに落ちた（Prisma クライアントをモジュール読み込み時に初期化しており、ダミーの `DATABASE_URL` で接続に失敗して起動ごと落ちた）
  3. Playwright の `webServer` 経由で起動するとクラッシュのログが取れず、原因を特定できなかった
  4. `localhost` が `::1`（IPv6）に解決され、IPv4 でリッスンするサーバーに繋がらなかった（Ubuntu 24.04）
  5. `curl -f` が 500 応答を失敗として扱い、起動しているのに起動待ちが終わらなかった
  6. `@nuxtjs/supabase` がビルド時に `SUPABASE_URL` / `SUPABASE_KEY`（`NUXT_PUBLIC_` 接頭辞なし）を読んで設定をバンドルに埋め込むため、画面が描画されなかった
- なぜ起きたか（根本原因）: CI はローカルと前提が違う（キャッシュの無いコールドスタート・ダミーの外部サービス・OS の名前解決）のに、ローカルで動く構成をそのまま持ち込んだ。加えてサーバーの起動を Playwright に任せていたため**起動ログが見えず**、1 つ直すたびに推測で次の原因を探すことになった。
- 教訓 / 次からどうする: CI の E2E は `nuxt build` した本番サーバーを**CI のステップで直接バックグラウンド起動し、ログをファイルに保存する**（起動待ちに失敗したらログを出力して落とす）。接続先は `localhost` ではなく `127.0.0.1` と明示する。起動待ちの判定は HTTP ステータスに関わらず「応答が返ったか」で行う。外部依存（DB クライアント等）はモジュール読み込み時に初期化しない。原因が見えないまま推測で直さず、**まず観測手段（ログ）を用意する**。
- 関連: `docs/troubleshooting.md`「E2E が CI で起動待ちタイムアウトする」（現行の手順）、`.github/workflows/ci.yml` の `e2e` ジョブ。当時の E2E は API を `page.route()` でモックしていたが、現在は実 DB で実行している（`.claude/rules/testing.md`「E2E（実 DB シナリオ）」）
